# Receiver Stats Interface

This document describes the existing `goesrecv` stats streams for future
monitoring, dashboard, or alerting work. It is documentation only; no monitor
implementation is included here.

## Overview

`goesrecv` publishes receiver statistics through nanomsg PUB/SUB sockets. There
are two independent stats streams:

- Demodulator stats: AGC, carrier tracking, and clock recovery state.
- Decoder stats: frame synchronization and error-correction results.

The sample configuration exposes them on TCP:

```toml
[demodulator.stats_publisher]
bind = "tcp://0.0.0.0:6001"

[decoder.stats_publisher]
bind = "tcp://0.0.0.0:6002"
```

A future monitor should connect with nanomsg `NN_SUB` sockets and subscribe to
the empty topic so it receives every message.

For local testing with the sample config:

```sh
nanocat --sub --connect tcp://127.0.0.1:6001 --raw
nanocat --sub --connect tcp://127.0.0.1:6002 --raw
```

## Transport Contract

The transport is nanomsg PUB/SUB:

- Publisher implementation: `src/goesrecv/stats_publisher.cc`
- Socket setup helper: `src/goesrecv/publisher.cc`
- External endpoints are configured in `etc/goesrecv.conf`.
- `Config::load` also appends internal `inproc://` endpoints for the built-in
  monitor in `src/goesrecv/config.cc`.

Each published message is one JSON object serialized as a string. The current
code appends a newline to each JSON string. Subscribers should parse each
received nanomsg message as one complete JSON object and should not depend on
the newline for framing.

`StatsPublisher::publish` checks for connected subscribers before sending. If no
subscriber is connected at that instant, the stats message is skipped.

## Demodulator Stream

The demodulator publishes stats from `Demodulator::publishStats` in
`src/goesrecv/demodulator.cc`. It runs inside the demodulator loop after each
block of sample processing.

Example message:

```json
{"timestamp": "2018-04-18T04:52:58.357Z","gain": 2.2494e+01,"frequency": 2.9813e+03,"omega": 1.6181e+00}
```

Fields:

| Field | Type | Meaning |
| --- | --- | --- |
| `timestamp` | string | UTC timestamp generated by `util::stringTime()`. |
| `gain` | number | Current AGC gain multiplier from `AGC::getGain()`. |
| `frequency` | number | Costas-loop frequency correction converted to Hz. |
| `omega` | number | Clock recovery samples-per-symbol estimate. |

Monitor guidance:

- Treat this as a high-rate stream relative to human dashboard updates.
- Aggregate over a display interval rather than rendering every sample.
- Average `gain`, `frequency`, and `omega` for a simple status view.
- Alerting on `frequency` should allow negative values.

## Decoder Stream

The decoder publishes stats from `Decoder::publishStats` in
`src/goesrecv/decoder.cc`. It emits one message for each packetizer result.

Example message:

```json
{"timestamp": "2018-04-18T04:54:22.974Z","skipped_symbols": 0,"viterbi_errors": 44,"reed_solomon_errors": 0,"ok": 1}
```

Fields:

| Field | Type | Meaning |
| --- | --- | --- |
| `timestamp` | string | UTC timestamp generated by `util::stringTime()`. |
| `skipped_symbols` | integer | Number of symbols skipped while acquiring frame sync for this result. |
| `viterbi_errors` | integer | Number of corrected Viterbi bit errors estimated by re-encoding/comparison. |
| `reed_solomon_errors` | integer | Number of Reed-Solomon corrected bytes, or `-1` when the packet was not correctable. |
| `ok` | integer | `1` if the packet was correctable and published, `0` if it was dropped. |

Monitor guidance:

- Count `ok != 0` as decoded packets.
- Count `ok == 0` as dropped packets.
- Exclude `reed_solomon_errors == -1` from corrected-byte histograms or sums.
- Track `skipped_symbols` as a lock/acquisition signal; sustained nonzero
  values may indicate receiver instability or signal loss.
- Average or histogram `viterbi_errors` over a display interval.

## Existing Aggregation Behavior

The built-in `Monitor` in `src/goesrecv/monitor.cc` subscribes to internal
`inproc://demodulator_stats` and `inproc://decoder_stats` endpoints. It parses
the same JSON objects and aggregates them over the configured display interval.

Current aggregation behavior:

- `gain`: average over the interval.
- `frequency`: average over the interval.
- `omega`: average over the interval.
- `viterbi_errors`: average over decoder messages.
- `reed_solomon_errors`: sum only nonnegative values.
- `ok`: count successes as packets and failures as drops.

When `--verbose` is enabled, those aggregates are printed as:

```text
YYYY-MM-DDTHH:MM:SSZ [monitor] gain: ..., freq: ..., omega: ..., vit(avg): ..., rs(sum): ..., packets: ..., drops: ...
```

The same monitor can also forward values to statsd using
`[monitor].statsd_address`.

## Suggested Shape for a Future Monitor

A future monitor should treat the stats interface as append-only JSON messages
from two sources:

```text
tcp://receiver-host:6001  demodulator JSON stream
tcp://receiver-host:6002  decoder JSON stream
```

Recommended initial implementation approach:

- Open one nanomsg subscriber per stats endpoint.
- Subscribe to the empty topic on each socket.
- Parse each received message as a complete JSON object.
- Add a local source label such as `demodulator` or `decoder` based on the
  socket that received the message.
- Aggregate into short windows such as 1, 5, or 10 seconds for dashboards.
- Preserve raw messages or rolling samples only when needed for debugging.

Recommended dashboard values:

| Display | Source fields |
| --- | --- |
| Signal gain | Average `gain` from demodulator stream. |
| Frequency correction | Average/latest `frequency` from demodulator stream. |
| Clock recovery | Average/latest `omega` from demodulator stream. |
| Packet rate | Count of decoder messages with `ok != 0` per interval. |
| Drop rate | Count of decoder messages with `ok == 0` per interval. |
| Viterbi health | Average or percentile of `viterbi_errors`. |
| Reed-Solomon health | Sum or percentile of nonnegative `reed_solomon_errors`. |
| Lock trouble | Count or max of `skipped_symbols`. |

## Compatibility Notes

The current field names are hard-coded in:

- `src/goesrecv/demodulator.cc`
- `src/goesrecv/decoder.cc`
- `src/goesrecv/monitor.cc`

Future code should tolerate extra fields and ignore unknown keys. It should also
treat missing fields as unavailable rather than fatal, so new receiver versions
can add or phase in stats without breaking monitors.

Because nanomsg PUB/SUB does not replay missed messages, a monitor should expect
gaps during startup, reconnects, or receiver restarts. For long-running history,
the monitor should store its own aggregates.
